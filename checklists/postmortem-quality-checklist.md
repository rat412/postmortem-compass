# Postmortem Quality Checklist — 交付前质检清单

逐项核对。任何一项不过 → 回去改，不要交付。

## A. 结构与可读性

- [ ] 开头 5 行内有执行摘要：发生了什么、影响多大、现在状态、最重要的一条改进
- [ ] 全文任意位置摘出来都能独立读懂（不依赖"见上文"）
- [ ] 原始聊天/日志没有大段粘贴，只有提炼后的事实
- [ ] 篇幅：SEV0–1 ≤ 5 页，SEV2 ≤ 3 页，SEV3 ≤ 1 页

## B. 不追责

- [ ] "原因"语境中没有任何人名（参与者致谢除外）
- [ ] 没有"人为失误""疏忽""没仔细检查"作为结论性表述
- [ ] 每个涉及人的句子都改写成系统/流程/工具视角
- [ ] 通读后确认：当事人读完不会想隐瞒下一次故障

## C. 时间线

- [ ] 所有时间戳统一时区并注明
- [ ] 每条标注 [FACT] 或 [INFER]
- [ ] 检测 → 诊断 → 缓解 → 恢复 四段齐全，每段有观察到的效果记录
- [ ] 故障前的相关变更（发布、配置、流量）已列入上下文事件

## D. 影响与定级

- [ ] 有 SEV 等级，且与定级表一致
- [ ] 持续时间、用户/流量影响、资损/数据影响至少有数字或"待补"标注
- [ ] 未按修复难度或政治压力定级

## E. 根因

- [ ] 导火索、根因、放大因素三层明确分离
- [ ] 根因落在可改进的系统/流程/工具上
- [ ] 每条原因链标注证据强度（已证实/高置信/待验证）
- [ ] 没有 [待验证] 假设混进结论

## F. 改进项

- [ ] 每项有 owner（角色/团队，非问责语境）、deadline、可验收的 done-criteria
- [ ] 覆盖四类：检测、预防、缓解、流程
- [ ] 无口号式条目（"加强""提高""重视"开头的一律打回）
- [ ] P0 项已明确"在哪个时间窗之前必须完成"
- [ ] 指定了跟踪人和下次回顾日期

## G. 元信息

- [ ] 标题、日期、作者角色、参与者、状态（草稿/评审中/已定稿）齐全
- [ ] 敏感信息（密钥、内部地址、客户隐私）已脱敏
